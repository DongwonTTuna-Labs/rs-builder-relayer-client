## Context

This design supports OpenSpec change `formalize-deposit-wallet-relayer-client` and capability `deposit-wallet-relayer-client`. The change formalizes the deposit-wallet relayer HTTP client behavior that already exists in Rust code, tests, and fixtures. It does not add new Rust behavior, new tests, or live production execution claims.

The current implementation is centered on `DepositWalletRelayerClient` in `src/deposit_wallet/http.rs`. That client owns a typed relayer URL, relayer-key auth, contract config, a local owner mutation store, HTTP transport settings, and a clock. It does not store an owner signer.

This document uses the PR 37 plan, Task 1 instruction evidence, current code, current tests/fixtures, and completed proposal scope as its input.

## Goals / Non-Goals

**Goals:**

- Define Rust code plus existing tests/fixtures as the normative source of truth for this OpenSpec change.
- Record known docs and plan divergences so later spec delta tasks don't turn stale aspirations into requirements.
- Keep a completed traceability matrix with the exact requirement names from `spec.md`.
- Describe the module architecture at the design level, with enough context to map requirements back to code and tests.
- Set a clear policy for normative external behavior versus internal design trace.

**Non-Goals:**

- No Rust source, test, fixture, docs, Cargo, archived spec, or main spec edits.
- No new public API promises beyond implemented code and existing tests/fixtures.
- No production live-execution readiness claim for deposit-wallet relayer mutation.
- No pUSD/CTF adapter calldata, consumer live gate, CLOB order flow, or future polling API requirement.
- No promotion of volatile internals, including `64 shards`, into an external contract.

## Decisions

### Source of Truth & Divergences

Decision: implemented Rust code plus existing tests/fixtures are normative for this OpenSpec change. Docs, plans, drafts, and roadmap prose are non-authoritative whenever they diverge from current code or tests. Later spec delta tasks must write requirements from code/test/fixture evidence, not from stale docs.

Rationale: this change formalizes PR 37 behavior after implementation. Treating older plans as normative would add unimplemented APIs to the spec and make the OpenSpec change inaccurate.

Alternative considered: use `docs/DEPOSIT_WALLET_RELAYER_DESIGN.md`, `docs/FORKED_RELAYER_CRATE.md`, and `docs/plans/02-deposit-wallet-http-client.md` as direct requirements. Rejected because they contain stale API shapes that don't match the current client.

### Normative vs Internal Detail Policy

Decision: only externally visible implemented behavior is normative. That includes public type/function contracts, wire DTO serialization, request ordering that protects credentials or owner state, documented error classes, state classification, and fixture-backed HTTP bodies.

Internal design trace may explain why a behavior exists, but it must not become an external contract. `64 shards` is the canonical example: `src/deposit_wallet/http/state.rs:12` currently sets the owner mutation store to 64 shards, and `src/deposit_wallet/http/state.rs:40` through `src/deposit_wallet/http/state.rs:50` builds those mutex shards. For OpenSpec, `64 shards` is internal design trace, not a normative external contract. The normative behavior is owner-scoped mutation coordination and local client-allocation state semantics, not the exact shard count.

Rationale: freezing incidental implementation details would make harmless refactors breaking changes. The spec should protect behavior consumers rely on, not private layout or tuning constants.

Alternative considered: include every code detail with a file:line citation as a requirement. Rejected because that would make the spec brittle and would conflict with the plan's explicit warning about volatile internals.

### Architecture Overview

Decision: document the implemented architecture by module responsibility and require later matrix rows to tie each requirement to the relevant module and test/fixture evidence.

- Client facade: `src/deposit_wallet/http.rs` defines `DepositWalletRelayerClient`, wires typed URL validation, auth, config, local owner mutation state, transport timeout, redirect policy, and debug redaction. It is the API surface for nonce lease, submit, mutation scope, and transaction read flows.
- Permit module: `src/deposit_wallet/http/permit.rs` defines mutation actions, scopes, default-deny gates, permits, owner serialization evidence, and reconciliation evidence validation. It keeps production mutation permits unavailable in this PR.
- State module: `src/deposit_wallet/http/state.rs` holds local owner mutation state, nonce-read reservations, submit reservations, ambiguous submit records, terminal observations, and reconciliation transitions.
- Submit module: `src/deposit_wallet/http/submit_flow.rs` implements `submit_wallet_create` and `sign_and_submit_wallet_batch_with_nonce_lease`. It enforces gate checks before HTTP/auth work, validates lease-bound signed batches, promotes nonce leases to submit reservations, and records ambiguous submit outcomes.
- Read module: `src/deposit_wallet/http/read.rs` implements WALLET nonce lease reads, internal nonce fetch parsing, single transaction lookup through `get_transaction_for_owner(owner, tx_id)`, and owner-aware transaction receipt classification.
- Wire type module: `src/deposit_wallet/types.rs` defines the `WALLET-CREATE` and `WALLET` request DTOs, submit response DTO, and serialization helpers used by fixtures.
- Signing module: `src/deposit_wallet/signing.rs` builds and validates DepositWallet Batch EIP-712 typed data, validates resource limits, verifies signer identity, and constructs signed batch requests from signed input.

Rationale: the OpenSpec change needs an architecture map before requirement groups append traceability rows. The module map keeps those rows consistent without making private internals normative.

Alternative considered: keep architecture out of design and make each requirement self-contained in `spec.md`. Rejected because the matrix needs a shared vocabulary for code areas and stale-doc divergence handling.
